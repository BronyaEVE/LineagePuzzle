# Representation ownership: the engine ships facts, the consumer renders

Status: accepted

A human-facing tool must pre-commit to one representation for every question — a compromise that demoting the global view (ADR-0002) could mitigate but not remove. We decided to move representation ownership out of the product entirely: the analysis core was extracted into a standalone package, **lineage_puzzle** (github.com/BronyaEVE/lineage_puzzle), which this repo consumes as a pinned git dependency — eliminating the engine fork that duplicated the analyzer in both repos. The package emits **statement facts** — one JSON line per statement, cross-product edges aggregated into `sources`, column mappings deduplicated, provenance as `script+seq+sql` pointers — a storage format designed for AI context consumption (~4.6× smaller than this repo's edges.jsonl: 2,484 edges → 536 facts measured). An Agent Skill wraps its CLI (`lineage-puzzle analyze/downstream/upstream/trace/stats`) and legislates ownership: **the engine owns the graph** (lineage never inferred by an AI reading the SQL itself), **the user owns the corpus** (which scripts enter the graph), **the AI owns representation** (the question chooses the form — mermaid, indented text tree, table, self-contained HTML — never the full graph). This is the third of three retreats, one layer apart each time: the view layer (global → neighborhood), the data-model layer (script → table), and now the product boundary (frontend → whoever consumes the facts).

**Why now:** per-question representation generation became economically viable with current AI — a human-facing UI must amortize one rendering across all questions; an AI renders each answer just-in-time. Visualization thus stopped being a product feature and became a per-question artifact.

**Consequences:** the web UI remains for human browsing but is no longer the sole consumption path; quality is now bounded by engine correctness rather than rendering, hence the sqllineage golden-set cross-validation (85.7% agreement at engine v0.2.0) as the standing quality instrument. Engine bugfixes flow one way: engine repo → tag → dependency bump here (see requirements.txt). What survived all three pivots unchanged — the AST analyzer, the entity-graph store, the provenance pointers — is the stable core; everything that died (G6 renderer, script-list navigation, visualization's primacy) was periphery, which is why each pivot cost a periphery rewrite, never a restart.
