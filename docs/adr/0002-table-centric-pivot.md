# Table-centric pivot: the table (not the script) is the navigation unit

Status: accepted

The tool was originally script-centric: the left panel listed scripts, and every question ("where does this table's data come from / go") required first finding the right script. We decided to make the **table the primary unit of navigation and storage**, because SQL declares sources but never consumers — upstream is written inside a script, while downstream is scattered across every other script, so a script-centric base makes downstream tracing structurally second-class. The table/column graph (tables.json + edges.jsonl) is the lineage source of truth, held in an in-memory cached DiGraph with bidirectional adjacency so upstream and downstream are symmetric O(1) queries; scripts are demoted to edge provenance (script_id/statement_seq) plus a management surface (upload/rename/delete/tags in a modal). The global node-link visualization is demoted to a non-default, explicit view — at scale it is unreadable regardless of renderer (edge-crossing hairball), so the center shows question-driven views instead: a table's depth-limited neighborhood subgraph (multi-select merges neighborhoods, with selected tables emphasized), and a column-level EXPLAIN-style text trace. A G6/canvas renderer migration was spiked and abandoned (see commit history): rendering was not the binding constraint.

**Consequences:** the UI has one navigation model (0 tables selected = 空态/全局, 1 = 邻域子图, N = 合并邻域); landing view is empty-state for large graphs (global only for ≤50 nodes or explicit click). See `CONTEXT.md` for the Role/Staging/Layer vocabulary this depends on; environment-neutrality (ADR-0001) still governs — nothing schema-specific is hardcoded.
